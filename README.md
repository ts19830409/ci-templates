# ci-templates — общий деплой для production-проектов (GitHub Actions)

Один переиспользуемый workflow для всех продактов: код, `.env`, запуск контейнеров,
тесты, миграции, статика и проверка ответа сайта. Каждый проект не копирует этот код,
а вызывает его одной ссылкой — починил здесь, работает везде.

Это аналог `ci-templates` на Gitea, но для GitHub Actions.

## Как подключить проект

В репозитории проекта создаётся файл `.github/workflows/deploy.yml`:

```yaml
name: Deploy

on:
  push:
    branches: [main]
  workflow_dispatch:

jobs:
  deploy:
    uses: ts19830409/ci-templates/.github/workflows/deploy.yml@main
    secrets: inherit
    with:
      project_dir: /srv/my_site
      project_name: my_site
      site_domain: ts-dev27.ru
      db_name: my_site_db
      media_bundle_url: https://github.com/ts19830409/my_site/releases/latest/download/media-bundle.tar.gz
```

Больше в проекте ничего править не нужно: файл деплоя уезжает в этот репозиторий.

## Что нужно один раз настроить на сервере проекта

1. Self-hosted раннер с метками `self-hosted`, `linux`, `x64` (уже стоит на vps-002).
2. Каталог проекта (`project_dir`) с первичным клоном — шаблон сам не клонирует
   пустой каталог, чтобы не затирать данные; клонировать вручную один раз.
3. `docker compose` в режиме `--build`, веб-контейнер должен называться
   `<project_name>-web-1`.

## Секреты

Значения **не хранятся в этом репозитории** — он публичный, в нём только шаблон.
Шаблон читает их из окружения `prod` вызывающего репозитория, поэтому в списке
`secrets:` они необязательные, а передаются через `secrets: inherit`.

| Секрет | Нужен для |
|---|---|
| `SECRET_KEY` | Django |
| `DB_PASSWORD` | подключение к БД |
| `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD` | отправка почты |
| `GITHUB_TOKEN` | клон репозитория (GitHub выдаёт сам) |

Секреты задаются один раз в настройках проекта: **Settings → Environments → prod**.
Держи их в окружении `prod`, а не в общем списке репозитория: тогда они не попадут
в джобы, которые это окружение не объявляют.

Пароли менять при этом не нужно — шаблон лишь читает текущие значения и пишет `.env`.

## Параметры (`with:`)

| Параметр | Обязательный | По умолчанию | Смысл |
|---|---|---|---|
| `project_dir` | да | — | каталог проекта на сервере |
| `project_name` | да | — | префикс контейнеров (`<name>-web-1`) |
| `site_domain` | да | — | домен(ы) для `ALLOWED_HOSTS` |
| `db_name` | да | — | имя базы |
| `db_user` | нет | `postgres` | пользователь БД |
| `smtp_host` | нет | `smtp.yandex.ru` | почтовый сервер |
| `smtp_port` | нет | `465` | порт почты |
| `compose_file` | нет | `docker-compose.yml:docker-compose.prod.yml` | файлы compose через `:` |
| `run_tests` | нет | `true` | гонять `manage.py test` |
| `media_bundle_url` | нет | пусто | архив медиа; **если пусто — медиа не трогаются** |
| `smoke_url` | нет | `http://127.0.0.1/` | что проверять после деплоя |

## Особенности

- Медиа заменяются **только** если задан `media_bundle_url`: без него шаблон папку
  `media` не трогает, и загрузки, сделанные через панель, переживают деплой.
- Секреты в `env` шага не кладутся — используется контекст `secrets`, потому что
  `GITHUB_TOKEN` в `env` на GitHub недоступен.
- `.env` создаётся в кавычках heredoc, поэтому `$` внутри паролей не съедается шеллом,
  и права выставляются `600`.
- Стек после деплоя остаётся запущенным (`--force-recreate`, финальный `up -d`),
  миграции и тесты повторяются 3 раза с паузой.
- Раннер выбирается по меткам `self-hosted, linux, x64` — одинаковые метки у всех
  продов допустимы: код деплоя идёт в конкретный `project_dir` на конкретном хосте.

## Ограничения

- Шаблон под Django (`manage.py test/migrate/collectstatic`) и compose. Для другого
  стека — копия этого файла в проекте с заменой этих шагов.
- Пул проектов на одном сервере: все они смотрят на одну и ту же машину раннера,
  различаются `project_dir` и `project_name`.
